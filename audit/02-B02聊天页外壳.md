## 用户会看到什么（先说这个）

一个第一次用这个 App 的人，进到聊天页，会经历这些：

**能用的**：输入框、加号面板（18 个功能磁贴，三页）、表情包抽屉、
语音输入、发图片/文件/拍照、拖文件进来、@ 文件、/ 斜杠命令、
长按消息的操作栏、模型选择、思考等级、会话锁。

**会困惑的**：
- 右上角没有「…」，所以「紧凑对话」「清空」「终端」「浏览器」「文件」
  只能从加号面板找 —— 加号面板有三页，新用户第一页看完就以为只有 8 个功能。
- 「快速模式」和「增强缓存」在说明书里有，在界面上永远找不到。
- 表情包抽屉顶栏只有「全部」「常用」两个标签，但登记表情时能选
  「撒娇」「嘲讽」等 10 个分类 —— 选完了回到抽屉，找不到那个分类。
- 让 AI 发一个表情包，AI 偶尔会在正文里打一个 `[翻:撒娇]`，
  这个标签不会显示（被删掉了），也不会真的去翻抽屉 —— 什么都不会发生。

**会踩坑的**：
- 把内核搞崩了（比如 rootfs 坏了），聊天页会变成一整屏
  「Kernel boot failed: -1」，**没有任何按钮**，只能退出 App 重进。
- 导出对话给别人看，对方只看到你的问题，看不到 AI 的回答。

## 逐条问题

### P-01 致命 · 已证实

**现象**：表情包档案（`stickers_catalog.json`）只要有一次读不出来，
程序会把图片目录重新扫一遍，把每个图片文件当成一个「新表情」登记回去 ——
标题写成「表情包」、分类写成「全部」、短描述写成「表情」。
原来的标题、分类、使用场景、使用次数全部被覆盖，然后立刻写回磁盘。

**证据**：

`Views/Chat/AIChatView.swift:7985-7992`（兜底重建的入口）
```
// 兜底容错恢复：若依然为空，扫描所有可能存过表情的目录自动恢复
if stickers.isEmpty {
    // [sticker-fix] 重建前先留现场：磁盘上若本来就有档案文件（只是这次没能读出来），
    // 先另存一份副本，避免占位重建把描述/分类静默覆盖后无从追溯。
```

`Views/Chat/AIChatView.swift:8011-8022`（写死占位值）
```
let item = StickerItem(
    id: id,
    title: "表情包",
    content: "",
    scenario: "",
    shortDesc: "表情",
    category: "全部",
    useCount: 0,
    imageFilename: imgFile,
    createdAt: Date()
)
```

`Views/Chat/AIChatView.swift:8031-8033`（立刻落盘，覆盖原文件）
```
if !stickers.isEmpty {
    nextNumericId = (stickers.compactMap { Int($0.id) }.max() ?? 0) + 1
    saveToDisk()
}
```

**为什么是问题**：
留了 `.before-rebuild-<时间戳>.json` 备份，但**界面上没有任何入口能恢复它** ——
用户不知道这个文件存在，也不知道要去哪儿找。
从用户视角就是「我的表情包全变成一样的名字了，还找不回来」。

更麻烦的是 `category: "全部"` 这个值：它不在 `store.categories`
（那 10 个分类）里面。所以：
- 抽屉顶栏只显示「全部」「常用」（`7008`），这些表情混在「全部」里能看见，
  但没法按分类找；
- AI 的提示词会把这些表情过滤掉（`8243` 排除了「全部」），所以 AI 看不见它们；
- 打开编辑时 `Picker` 的选项里没有「全部」，选中项会落空。

**原因**：兜底重建把「恢复可用的最小信息」当成了目标，
但没考虑「分类是索引键」这件事 —— 写一个不在分类表里的分类，
等于把这些表情从所有索引里摘出去。

**建议方向**：重建时按文件名反推分类（图片所在子目录名），
或者至少写进 `categories` 里并给出「请重新分类」的提示。
备份文件要在设置里给一个「从备份恢复表情档案」的入口。

**影响范围**：所有用表情包的人。触发条件是档案解码失败
（历史上有过：日期编码策略不一致导致整份丢弃，注释 `7927-7931` 记着）。

### P-03 严重 · 已证实

**现象**：只读查看「另一台设备上的会话」这条链路，**整条是死的**。
就算打通了，在正式版（Release）里它还会露出一个输入框，

**没有任何地方把它 `insert` 进视图树。**

第二层 —— `AIChatView` 的只读分支在正式版里被跳过。

```
#if DEBUG
if isReadOnly {
    forkBanner

    inputBar

#else
inputBar          ← Release 走这里，不管是不是只读

没有 toast、没有提示、按钮也不置灰（`canSend` 在 `4902` 不检查 `remoteDeviceId`）。

**为什么是问题**：三层叠起来，用户会经历
「看不到入口 →（假设入口修好了）看到一个能打字的框 → 打字 → 按发送 → 什么都没有」。

(c) 只保留 `SessionForkManager.forkSession`（把远程会话复制成本地会话），

**影响范围**：功能本身没人能用（入口没了），所以实际伤害是
「约 500 行代码 + 一个 9,000 行文件里的分叉路径」白养着，
外加以后谁想修这条链路会踩三层坑。

### P-04 严重 · 已证实

**现象**：用「导出对话」把聊天导成 markdown，导出来的文件里
**AI 说的话全是空的**，只剩用户自己的消息。

**证据**：

`Views/Chat/AIChatView.swift:2194-2200`
```
var text = "# OpenMinis 对话记录导出\n\n"
for msg in vm.messages {
    let personaName = SoulStore.cachedMetadata.name.trimmingCharacters(in: .whitespacesAndNewlines)
    let roleName = (msg.role == .user) ? "我" : (personaName.isEmpty ? "助手" : personaName)
    text += "### \(roleName):\n\(msg.content)\n\n"
}
```
只读 `msg.content`。

而助手消息的 `content` 在流式过程中**从来没有被写过**：
`Agent/Chat/AIChatViewModel+SSEStream.swift:478` 写的是 `block.content`：
```
block.content = assistantText
```
全仓搜索 `messages[...].content =` 和 `msg.content =`，**零结果**。
新消息创建时是空的：`AIChatViewModel.swift:5447`
```
messages.append(ChatMessage(role: .assistant, content: "", blocks: []))
```

**反证（同一个文件里已经修过同一个坑）**：
`Views/Chat/AIChatView.swift:6709-6718`（语音纠错用的上下文构建）
```
var text = msg.content
if msg.role == .assistant, !msg.blocks.isEmpty {
    let blockText = msg.blocks
        .filter { $0.kind == .text }
        .map(\.content)
        .joined(separator: "\n")
    if !blockText.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty {
        text = blockText
    }
}
```
注释写得很清楚：「Assistant turns keep their prose in `blocks` (text blocks),
not in `content` — reading only `content` silently dropped every AI
reply from the correction context.」

**同一个文件里，同一个坑，一处修了一处没修。**

补充：从数据库重新加载的消息是有 `content` 的
（`Agent/Chat/ChatStore.swift:5597` `ChatMessage(role: uiRole, content: textContent, ...)`，
`textContent` 在 `5482-5486` 和 `5585-5586` 由 parts 拼出来）。
所以症状是「**本次会话新产生的回复导出为空，重进一次会话再导出就有了**」——
这比全空更糟，因为用户会以为导出功能是好的。

**为什么是问题**：用户导出聊天记录是为了存档/分享/喂给别的模型。
导出一份没有 AI 回答的记录，等于白导。

**原因**：`ChatMessage` 有 `content` 和 `blocks` 两份文本，
历史遗留的「content 是显示文本」约定在新流式路径里没守住。

**建议方向**：把 `6709` 那段 fallback 抽成一个 `ChatMessage.displayText`
属性，导出、纠错、复制、分享全部走它。**不要再各写一份。**

**影响范围**：所有用导出功能的人。而且症状会让人误判成「导出正常」。

### P-05 严重 · 已证实

**现象**：内核启动失败时，聊天页变成一整屏红色错误文字，
**没有任何按钮** —— 没有重试、没有「查看日志」、没有「重置 rootfs」。
用户唯一能做的是退出 App 再进（而且再进还是失败）。

**证据**：

`Views/Chat/AIChatView.swift:2797-2813`（失败态的全部 UI）
```
case .failed(let msg):
    ZStack {
        ChatColors.background
            .ignoresSafeArea()
        VStack(spacing: 12) {
            Image(systemName: "exclamationmark.circle.fill")
                .font(.title2)
                .foregroundStyle(ChatColors.destructive)
            Text(msg)
                .font(.subheadline)
                .foregroundStyle(ChatColors.destructive)
                .multilineTextAlignment(.center)
                .padding(.horizontal, 40)
        }
    }
    .transition(.opacity)
```
只有图标 + 文字。零按钮。

`Agent/Chat/AIChatViewModel+Misc.swift:12-14`（无法重试）
```
func ensureKernelBooted() {
    guard kernelStatus == .notBooted else { return }
    kernelStatus = .booting
```
失败后 `kernelStatus == .failed`，`guard` 直接 return。
全仓搜索 `kernelStatus = .notBooted` **零结果** —— 状态机没有回边。
全仓搜索 `retryKernel` / `rebootKernel` **零结果**。

**为什么是问题**：这是死胡同。用户能做的只有：
退出 App → 重进 → 同样的错误 → 循环。
错误文字是英文技术错误（`"Kernel boot failed: -1"`），
没有指向任何可以自己动手的地方（比如「设置 → Rootfs 管理 → 重置」）。

**原因**：内核状态机写成了单向的，UI 只负责显示。

**建议方向**：失败态加两个按钮：
「重试启动」（把 `kernelStatus` 复位成 `.notBooted` 再调 `ensureKernelBooted`）、
「打开 Rootfs 管理」（`DeepLinkRouter` 已经支持 `minis-clone://settings/rootfs`）。
再补一句人话解释（比如「内核没能启动，通常是系统镜像损坏，可以在 Rootfs 管理里重置」）。

**影响范围**：所有遇到 rootfs 损坏 / 存储不足 / 内存不足的人。
这类错误不可恢复的话，App 等于砖了。

### P-06 严重 · 已证实

**现象**：用户在设置里调「字号」，**消息气泡会变大，但聊天页其它一切都不变** ——
输入框、加号面板、表情抽屉、工具栏、时间分隔线、用量面板、语音设置弹窗，
全都保持原样。调「正文字体」也一样。

**证据**：

全文件统计（脚本实测）：
```
.system(size: 出现次数: 80
其中带 relativeTo: 的: 0
.font(.caption/.body 等语义字号: 44
```

`.system(size: 11)` 这种写法是**固定字号**，不跟 `dynamicTypeSize` 走。
只有 `.font(.caption)` / `.font(.body)` 这类语义字号、或者
`.system(size: 11, relativeTo: .caption)` 才会缩放。

`Views/ContentView.swift:2125` 和 `:2142` 把 `.appFontScale()` 挂在了
列表列和详情列上，而 `Shared/FontSettings.swift:227-237` 的实现是
```
content.dynamicTypeSize(fontSettings.appBaseScale.dynamicTypeSize)
```
`dynamicTypeSize` 只影响语义字号，**对 80 处写死的 `.system(size:)` 完全无效**。

字体族更直接：全文件搜索 `MinisThemeShape.fontFamily`、`scaledMessage`、`scaledApp`
**零结果**。
而消息气泡是用的：`Views/Chat/ChatMessageViews.swift:80`
```
.font(MinisThemeShape.fontFamily.font(size: FontSettings.shared.scaledMessage(16.5)))
```

**为什么是问题**：用户花时间调设置，只有气泡变了。
这不是「设置没生效」，是「一半生效」—— 比完全不生效更让人困惑，
因为用户会以为自己调错了地方，反复试。

另外这也影响无障碍：iOS 的「更大字体」辅助功能对这些文字完全无效。

**原因**：这一层 UI 是逐轮手写堆出来的，每次加新控件都是 `size: 11`、`size: 12`
照抄上一处，从来没有统一的字号 token。

**建议方向**：先定 3-4 个字号 token（比如 `caption=11 / body=13 / title=16 / huge=34`），
放一个 `ChatFont` enum，全部改成 `ChatFont.caption`。
再用 `FontSettings.shared.scaledApp(...)` 包一层。
这一条工作量不小（80 处），但只做一次就永久解决。

**影响范围**：所有调过字号/字体的人 + 所有需要大字体的用户。

`Views/Chat/AIChatView.swift:3481`（加号按钮，走 CSSThemeVariables + 系统外观）

```

内部走 `AppearanceStudio.shared.activeVariant`。

**影响范围**：所有用「强制浅色/强制深色」的人。
默认跟随系统的人看不出问题 —— 所以这个 bug 藏得很深。

1. 标签被删，用户看不见（好）；
2. AI 没拿到目录，但它在自己的上下文里看到自己输出了这个标签，

(b) 真的实现：检测到 `[翻:x]` 时，在工具循环里自动注入一次

**最省事、最不容易出错的是 (a)。**

**影响范围**：所有开了表情包的人。触发概率取决于模型多爱输出这个标签 ——
提示词明确教了，所以会经常触发。

## H 用户视角：把这一页真走一遍

### 这是给谁用的、解决什么问题

聊天页是整个 App 的主场 —— 99% 的时间用户都在这儿。
它要解决的是「跟一个 AI 说话」这件事：打字、发表情、发图片、
发文件、让它干活、看它干活、在它干错时叫停。

第一次用的人能不能自己找到入口？**能，但只找到一半。**

打开就是一个空会话，中间有一张引导卡（只在从没用过的人面前出现，
`2975-2979`），写着「每个会话有自己的 workspace/attachments/offloads/browser，
共用的有 shared/skills/memory/mounts」。这段对新人来说**是纯噪音** ——
他还没开始聊，不知道 `/var/minis` 是什么，也不会去点「Browse Chat Files」。

真正需要的「你可以打什么」一个字没有。

### 从点进去到完成，几步，哪一步会卡

**打字聊天**：点输入框 → 打字 → 按发送。3 步，不卡。这是最顺的一条。

**发表情包**：
1. 点「+」（`3486`）
2. 面板弹出来，第一页 8 个磁贴 → 找「表情包」
3. 抽屉切过去
4. 顶栏只有「全部」「常用」两个标签（P-08）
5. 选一个 → 它挂到输入框上方变成待发卡片
6. 按发送

**6 步**，而且第 4 步就卡住了 —— 如果用户之前按分类整理过，
现在找不到自己的分类。这是最容易让人「算了不发了」的地方。

**让 AI 发表情**：直接说「发个委屈的表情」，AI 输出 `[贴:012]`，
界面渲染成图片。**这个体验是好的** —— 前提是 P-01 没把编号搞乱。

**发图片**：点「+」→ 照片与视频 → 系统相册 → 选 → 等缩略图 → 发送。
选图时有加载占位（`1327-1355` 的 placeholder 机制写得不错），
多选时每张都是并发加载的，失败会变成错误 chip。**这一段体验很好。**

**导出对话**：点「+」→ 第三页 → 导出对话 → 分享面板。
**走完发现 AI 的话全是空的**（P-04）。这是「做完之后用户什么都没得到」的典型。

**锁着的时候想解锁**：锁屏遮罩出现 → 点 → Face ID → 进。
但如果 Face ID 失败一次，会变成「Tap to try again」，
而且**遮罩只盖住消息区**（P-12）—— 用户能看到自己打了一半的草稿，
这种「半遮半掩」比全遮更让人不安。

### 顺不顺

**反应快不快**：输入框的布局用了三重防抖（`3990-4215`），
每次输入框高度变化都要等 380ms + 320ms 才稳定。
所以从「点加号」到「面板完全展开、消息区让开」有**约 0.7 秒的视觉抖动**。
注释里七次修同一个变量（`T-voice-inputbar-*` 系列）说明这块一直不稳。

**有没有等待却没提示**：
- 会话加载有「三点」卡（好）
- 内核启动有「Booting Kernel」（好）
- **但内核启动失败没有任何出路**（P-05）
- 表情包 AI 识图有「AI 识别情绪中…」（好）
- **批量导入失败不提示**（P-11）

**做错了能不能撤回**：
- 删消息：有二次确认（`944-957`），删 AI 回复不连累用户消息（`10-20` 刚修的）
- 清空对话：有二次确认
- 压缩历史：有二次确认 + 摘要面板里能「Revert Compact」（`6383`）
- **但清空对话不删文件**（P-22），删了也没法恢复

**结果是不是用户想要的**：
导出（P-04）、表情分类（P-08）、AI 翻抽屉（P-09）这三处，
用户做完了但结果不是他要的，而且**界面上没有任何提示说「这没做成」**。

### 做完之后得到了什么

- 聊天记录：得到了，存在本地
- 导出文件：**得到了一个残缺的文件**
- 表情包整理：**整理完发现分类看不见**
- 快速模式：**根本打不开**
- 会话锁：得到了，但漏一半
